answers — the same shape as 2026-08-31, and the third sitting running to produce
adjustments rather than confirmations. **Light mode is still unseen**, on a sheet
that put it first specifically so it could not escape a fifth time.

Two are defects and were **executed the same session**; three are decisions and
are not this file's to make.

**1 — Production Plan / Combined cannot scroll. Fixed.** The by-study plan is
inside a `SingleChildScrollView`; the combined plan is inside an `Expanded` with
nothing scrolling above it, and it asked `resultTable` for `maxHeight: null` —
which that file documents as meaning *the page I sit in scrolls*. Nothing did, so
the table grew past the pane and **clipped**: 130 orders and no way to reach row
30. Its own comment — *"no cap and filling the pane... as tall as the window"* —
was the intent, and `maxHeight: null` was the wrong lever for it. It now takes
the pane's own constraint, which is the mechanism §12.6 already built: a bounded
pane whose heading holds still and whose two bars pin to its edges.

**5 — `Q4 2...`. Fixed.** A column is a declared width (#16) with a 16 pt sort
arrow reserved beside the label whether or not it is the sorted one. 72 was
chosen for `Aug 2026`; `Q4 2026` and `H2 2026` are a character wider, so they
ellipsised — a heading naming a quarter without saying which year, on a grid that
has spanned three of them since phase 9. Quarter and semester columns are 96 now;
month and year keep 72, because `733/499` needs it and `2026` fits it. The width
is read once and handed to the chart's hover strip, which had been reading the
month constant directly — right at month grain and wrong at every other, the
exact fault #16 exists to prevent.

*Recorded and not done: measuring the heading at runtime*, which is what the row
height does one screen above and would be locale-proof. It makes the column width
depend on the font, and the test font here is far wider than the shipping one, so
every existing width assertion in `period_matrix_test.dart` would become a
different question. This is a visual fix and this map settles those by driving.

**A sixth finding arrived by using the app rather than by walking the sheet.** *"I added more
operators per shift to coating. But it didn't increase the capacity."* It is not a bug —
`working_calendar.dart:361` gates on `count > 0` and §7.5 said so twice — but the **model was
wrong**, and the field is what showed it: a CNC is machine-paced, a spray booth is not.
[Operators scale throughput at labour-paced stations, and the model denies it](https://github.com/matheus-sancha/FlowMap/issues/20)
carries it, and it is the one thing that has moved this map's Out of scope line. Phase 10.

**2, 3 and 4 were decisions rather than defects.** All three were settled the same session and
2 and 3 are **built**; 4 is a rule rather than a feature and is applied:

- **A start/end date field with a calendar helper, driving the slicer.** This
  partly reverses #17, which *deleted* `showDateRangePicker` — and deleted it
  because it chose **days** while the button printed only year and month, so
  15 Jan–20 Feb read back as `2026-01 → 2026-02`. A calendar picking days brings
  that back; a calendar picking months is a calendar with its days disabled. The
  question is which grain the field commits to, and what happens to #17's
  guarantee that the empty range is unreachable.
- **"Workcenter Type" as a third grouping.** #9 chose two and retired the pivot
  to get *one figure at one grain instead of two at two*. A type row is
  arithmetically the line row's shape — everyone's demand at the stations of that
  type over those stations' capacity — so the bands carry over, but it inherits
  the line grouping's named cost: rows overlap where a type spans lines, so they
  do not sum and the TOTAL row can equal one of them.
- **Capitalize each word in buttons.** The trap is that this is an **English**
  convention. Title Case is normal for en-US UI labels; Spanish and Portuguese
  use sentence case, and *"Incluir En Simulación"* reads as a mistake to a native
  reader. Applying it to all three ARB files would make two of them wrong, so the
  question is whether the rule is per-locale — and if it is, it is a rule about
  the three files rather than a find-and-replace.

> - The workcenter capacity type "i" icon, I'm trying to see the tool tip but can't.
> - Also When the workcenter capacity type is set to Machine Pace and I can process 2 orders at the same time, how we this is treated in the occupation graph? Because the capacity hours will be the same but can process multiple orders.

**The sitting reached light mode.** Five sittings in, section 1 was finally opened — and it did not
survive first contact: the finding is not about a colour but about the *cost of looking*. Two
defects, both **executed the same session**; one question, answered from the code and **not** a
defect. Sections 2–7 remain unwalked.

**1 — There is no theme control, and that is why light mode escaped four sittings. Fixed.**
`app.dart` handed `MaterialApp` a `theme:` and a `darkTheme:` and no `themeMode:`, so brightness
belonged to Windows. Seeing the light palette meant changing an OS-wide personalisation setting and
changing it back — a cost paid on the *reader's whole desktop*, for a look at one app. That is a
sufficient explanation for four misses, and it makes this a **drive-instrument defect** rather than
a preference: the sheet's own section 1 was unaffordable.

`AppThemeMode` follows `AppLanguage` line for line — named values, `fromStored` by name so
reordering cannot rewrite an existing install, `system` as the default so an install that never
opens Settings is unchanged. It is the third card under *Settings → Display*, and last of the
three: language and date format can each make the screen unreadable, and this one cannot.

*Recorded and not done:* `app.dart` handing the mode over is still checked only by driving. The new
tests copy those two lines rather than mounting `FlowMapApp`, which needs the router, which needs
the database — the same named gap `language_test.dart` carries for `locale:`.

**2 — The Capacity Type `ⓘ` cannot be tapped. Fixed, and it was Flutter rather than us.** The icon
sat inside `InputDecoration.label`, and `_RenderDecoration.hitTestChildren` hit-tests the label
through its **paint offset only** — its own comment says *"the label must be handled specially
since we've transformed it"* and then handles it like every other child, ignoring the scale a
floating label is painted through. So the icon is painted in one place and hit in another. This
dropdown always floats its label, because it always has a value.

It was **the only site of its kind in the app**: eighteen other fields hang their help on
`suffixIcon`, which is hit-tested normally. It now uses `namedHelp` above the control — the pattern
the icon grid two lines below it already follows.

**3 — Parallel capacity is already in the denominator. Not a defect, and nothing to change.** The
premise — *"the capacity hours will be the same"* — is the part that is wrong. A workcenter carries
`parallel_capacity` (*"Orders at once"* in the editor), it reaches the engine as `units`, and
`engine.dart:1290` and `:1310` multiply by it in **both** capacity paths, the run total and the
monthly rows: `openTimeBetween(...) * units`. A station set to 2 has **twice the capacity hours**,
so an unchanged demand halves its occupation. The field's help already says so — *"twice the
capacity everywhere it is measured"* — and one station in the live plant, **TTAT**, is already set
to 2.

*Worth confirming on screen anyway*, because it has never been driven: TTAT's occupation should
read half what its raw demand-over-one-machine would. Added as the second half of check 32.
